# چک‌لیست تحویل به بک‌اندکار

این ریپو فرانت‌اند خالص است. `scripts/api.js` درخواست‌ها را با `fetch` می‌فرستد؛ هیچ بک‌اند، mock server، شبیه‌ساز، دادهٔ نمونه (seed) یا fallback ذخیره‌سازی محلی برای داده‌ها در این ریپو وجود ندارد:

- **نشست پیش‌فرض/نمایشی حذف شده است.** مرورگر تازه در حالت «ورود / عضویت» است و نشست فقط از پاسخ سرور (`/auth/login`) ساخته می‌شود.
- **دادهٔ نمونهٔ سفارش/کاربر/پیام حذف شده است.** پنل تا وقتی سرور داده ندهد، فهرست خالی نشان می‌دهد.
- **fallback محلی تبلیغات حذف شده است.** خطای سرور همان‌طور که هست به اپراتور نمایش داده می‌شود.
- **helper توسعهٔ `/auth/promote` از `appApi` حذف شده است.**

چند قابلیت هنوز state را مستقیم در مرورگر نگه می‌دارند (جدول پایین)؛ اتصال API به‌تنهایی آن داده‌ها را مهاجرت نمی‌دهد.

---

## پیکربندی اتصال

پیش از `scripts/api.js` در هر صفحه، در صورت نیاز به origin جدا، آدرس پایه را تنظیم کنید:

```html
<script>
  window.APP_CONFIG = { apiBaseUrl: "https://api.yoursite.com" };
</script>
<script src="../scripts/api.js"></script>
```

اگر `apiBaseUrl` خالی باشد، درخواست‌ها به همان origin می‌روند. `window.APP_CONFIG.apiBaseUrl` تنها پیکربندی لازم است؛ هیچ script تگ یا فایل mock برای حذف وجود ندارد.

### همه اندپوینت‌ها

```
احراز هویت    /auth/register  /auth/login  /auth/logout  /auth/me
              /auth/forgot-password

کاربر         /profile/update  /profile/password
              /commerce/my-orders      /commerce/entitlements
              /support/my-messages

خرید          /commerce/payment  /commerce/cancelled  /commerce/coupon

پشتیبانی      /assistant/chat   /support/messages  /support/reports
              /newsletter/subscribe

محتوا         /content/items/:id

پنل           /admin/users     /admin/products   /admin/orders
              /admin/messages  /admin/reports    /admin/settings
              /admin/notifications  /admin/audit/:staffId
              /admin/content-items  /admin/pending-changes
```

### رفتار خطا

- پاسخ ناموفق → `ApiError` با `status` و پیام سرور
- تایم‌اوت → کد `408`
- قطع ارتباط → کد `0`

هر صفحه‌ای که این‌ها را می‌گیرد، پیام را به کاربر نشان می‌دهد.

## ⚠️ سه نکتهٔ امنیتی که سرور باید رعایت کند

### ۱. مجوز دانلود را از جدول سفارش بساز

```
POST /commerce/entitlements  →  ["acc-101", "acc-102"]
```

**هرگز** به فهرستی که کلاینت می‌فرستد اعتماد نکن. این باید از سفارش‌های `success` همان کاربر ساخته شود.

### ۲. قانون دسترسی اعلان‌ها را سمت سرور اعمال کن

نقش «ادمین» **نباید** ردیف‌های `staff` و `report` را دریافت کند — نه اینکه دریافت کند و کلاینت پنهانش کند. فیلتر فعلی در مرورگر فقط برای نمایش است.

### ۳. حساب غیرفعال را در هر درخواست بررسی کن

فرانت فقط توکن ذخیره‌شده را می‌فرستد و هیچ بررسی محلی ندارد. سرور باید در **هر** درخواست احرازشده وضعیت حساب را چک کند؛ یک توکن معتبر از حسابی که بعداً مسدود شده، نباید بتواند خرید یا پیام ثبت کند.

### ۴. مبلغ و وضعیت پرداخت را از خود درگاه تأیید کن

الان وضعیت از پارامتر URL خوانده می‌شود که کاربر می‌تواند دستکاری کند. در نسخهٔ واقعی، callback درگاه باید سمت سرور تأیید شود.

## وضعیت‌های هنوز محلی

این‌ها در کد فعلی خارج از `appApi` ذخیره/خوانده می‌شوند. بعضی‌ها ترجیح دستگاه‌اند، اما مواردی که بر خرید، مجوز یا دسترسی اثر دارند باید در سرور دوباره اعتبارسنجی شوند.

| دسته | مسیرهای/کلیدهای نمونه | نکتهٔ بک‌اند |
| --- | --- | --- |
| state نمایشی دستگاه | `benamacademyLastSeenOrderCount`، جمع‌شدن ویجت تبلیغ | می‌تواند محلی بماند. |
| سبد و اطلاعات موقت خرید | `benamacademyCart`، `benamacademyCheckout`، مشخصات خریدار | سرور مبلغ، موجودی و هویت خریدار را مستقلاً اعتبارسنجی کند؛ به localStorage اعتماد نکند. |
| نشست و نقش توسعه | `benamacademySession` (توکن صادرشده از سرور)، `adminDev` (فقط تا وقتی `ADMIN_AUTH_ENABLED=false` است) | نشست مدیر پیش‌فرض حذف شده؛ `adminDev` فقط ابزار کنسول برای تست نقش‌هاست و با فعال‌شدن احراز هویت سرور بی‌اثر/حذف می‌شود. |
| محتوا و تنظیمات | `benamacademyAddedItems`، state منو، سکشن‌ها و تنظیمات | برخی بخش‌ها هنوز بین مرورگرها همگام نیستند؛ منبع حقیقت سرور باید مشخص شود. |
| حالت تعمیر | `benamacademyMaintenanceMode` | localStorage فقط می‌تواند cache/نمایش باشد؛ قفل واقعی باید روی سرور اعمال شود. |

## ❌ آنچه هنوز تمام نیست

### رمز عبور پنل

```js
// scripts/admin/auth.js
function verifyAdminPassword(input) { ... }
```

رمز فعلاً در `localStorage` است. این **عمدی و موقت** است و در سه جای کد `BACKEND NOTE` دارد.

بک‌اندکار باید:

```js
// به‌جای بدنهٔ فعلی:
return appApi.admin.auth.verifyPassword({ password: input });
```

بقیهٔ پنل فقط `verifyAdminPassword()` را صدا می‌زند، پس هیچ فایل دیگری تغییر نمی‌کند. سرور باید با `bcrypt` یا `argon2` هش کند.

### احراز هویت پنل در فرانت‌اند فقط حالت توسعه است

```js
const ADMIN_AUTH_ENABLED = false; // scripts/admin/auth.js
```

این flag **عمداً `false` مانده** تا پنل در نبود سرور قابل توسعه و تست باشد؛ `scripts/admin/auth.js` هم ابزار کنسولی `adminDev` را فقط در همین حالت روی `window` می‌گذارد. (نشست مدیر نمایشی `app-shell.js` قبلاً حذف شده است.)

برای اتصال بک‌اند:

1. `ADMIN_AUTH_ENABLED` را در `scripts/admin/auth.js` (یک خط) `true` کنید — از این لحظه پنل بدون نشست معتبر به sign-up ریدایرکت می‌کند.
2. مهم‌تر: سرور باید دسترسی به **هر** endpoint با پیشوند `/admin` را خودش احراز هویت/مجوزدهی کند. گیت کلاینت فقط UX است و قابل دور زدن است؛ صرفاً `true` کردن flag امنیت نمی‌سازد.
3. پس از فعال‌شدن احراز هویت واقعی، بلوک `adminDev` و `mintAdminSession` در `scripts/admin/auth.js` را حذف کنید.

### آپلود فایل

تصاویر فعلاً به شکل data URL منتقل می‌شوند چون اندپوینت آپلود وجود ندارد. لازم است:

```
POST /support/reports/evidence   →  { url: "..." }
POST /admin/products/image       →  { url: "..." }
```

و همان بررسی نوع و حجم که در کلاینت هست، سمت سرور هم تکرار شود.
